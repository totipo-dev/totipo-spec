# Totipo v1/r15 state model simplification report

## 1. Scope

Create Totipo Vault Format v1/r15 from committed r14, intentionally simplifying state semantics. Work is confined to `totipo-spec`; no `totipo-java` or downstream implementation files are changed. Protocol version 1, semantic version allocations, bootstrap version, namespaces, and fixed crypto/wire fixtures remain unchanged. This report and its audit attachment are intended for the r15 spec-repository commit after approval; this working-tree preparation does not itself commit or publish them.

## 3. Design motivation

An unreliable synchronized directory and a local journal cannot establish a globally complete or fresh transaction. r15 uses authenticated immutable objects and explicit causal interpretation for the guarantees the protocol can actually provide. Writer decisions are relative to accepted evidence; later valid history is normal concurrency.

## 4. r15 security model

Section 3 visibly separates trusted local execution, authoritative local identity/private custody, advisory history, and untrusted/unreliable synchronized transport. Content validation remains mandatory for external bytes. Established vault identity remains protected by the independent local binding. Same-privilege hostile OS/filesystem race immunity remains optional hardening under the unchanged r14 trust boundary.

## 5. Authoritative local state

VAULT publication, the local VAULT_BINDING, and private device-key custody retain strong crash safety. An existing mismatching root is rejected, not treated as concurrent TOKEN state. Corrupt authoritative anchors require explicit recovery/reconfiguration. The history cache is not part of this authority.

## 6. Advisory local history

Section 34 permits, but does not require, remembered IDs, routing summaries, head sets, optional authenticated copies, startup indexes, and UI history. Baseline clients may retain zero cross-run history and need not synthesize history-derived diagnostics. Mere absence of the feature is not HISTORY_MEMORY_LOST. Authoritative local binding/private custody and accepted-snapshot graph interpretation remain mandatory.

No cache format or journal is normative. Claimants of the optional advisory-history capability must keep remembered evidence diagnostic-only, discard corrupt cache, and preserve otherwise valid use/publication after cache failures. Current accepted objects may be used immediately without committing a cache record.

## 7. Unreliable synchronized transport

Sections 3, 4, 24, and 39 explicitly permit delay, omission, old subsets, hidden later arrivals, and removal of visible objects. Neither local scans nor acknowledged local publication prove remote completeness, freshness, or propagation. An unavailable object is unavailable in that local observation; absence is not proof of global deletion, rollback, or invalid prior authorship.

## 8. Accepted snapshot model

ACCEPTED_SNAPSHOT contains successfully read, envelope/keyed-ID authenticated, classified, appropriately accepted current object evidence plus acknowledged locally authored objects during the process as appropriate. Successive observations may add/remove evidence. Graph indexes are derived and disposable. The model's Snapshot method detaches planning evidence; advisory memory remains separate.

## 9. Snapshot-based authorship

Sections 32, 33, and 47 set parents exactly to H from accepted planning snapshot S. An ordinary update needs one understood complete value; new-token creation permits empty H. Visible conflict needs confirmation, and an opaque current TOKEN head blocks that TOKEN. Signed parents attest the accepted planning heads, not absence of hidden remote history or stability until publication.

## 10. Concurrency semantics

Section 28 includes A → B and A → C, with C arriving before or after B publication. B and C remain ordinary valid concurrent history. Equal complete values converge semantically; different values conflict. New cases execute both arrival orders and an ambiguous retry sibling. No previously published object is rolled back.

## 11. Ordinary freshness simplification

The ordinary publication-time frontier linearization is removed. Another TOKEN, DEVICE display, unrelated provenance/availability, or sibling discovery cannot retroactively invalidate a plan. A conservative restart is permitted product behavior, not v1 conformance. There is no vault owner revision or publication epoch in the model.

## 12. Confirmation freshness simplification

Section 27 binds the human decision to TOKEN_ID, exact supported visible H, complete alternatives, desired complete value, and intent. The last-moment check remains for conflict resolution. Newly learned material TOKEN semantic information invalidates consent even if heads later look the same; unrelated TOKEN/DEVICE/discovery events do not. Plan/Observe/Publish and cases exercise these distinctions. Unit tests also change desired value and intent after confirmation and require rejection.

## 13. Removed unavailable-state confirmation

A remembered absent head is excluded from accepted H. Its absence can warn of regression but no longer mandates Section 27 confirmation or VALUE_INCOMPLETE_UNAVAILABLE. Existing missing-peer/current cases now allow the remaining understood value. Known visible differing complete values still require explicit whole-state confirmation.

## 14. Discovery semantics

PROCESSING_INCOMPLETE is diagnostic. Resource/read/enumeration failures do not authenticate anything and must be disclosed. Accepted objects remain usable. The incomplete-snapshot case exercises ordinary use and publication; storage tests preserve authenticated earlier observations when a later read fails. Resource-complete reset transactions and global READY gates are removed.

## 15. Local history regression warnings

HISTORY_REGRESSION indicates current evidence does not incorporate some remembered history. Warnings never change the current graph or eligibility. The reference warning model considers present IDs and compatible direct signed incorporation without traversing cache-only intermediates. The regression-and-return case excludes remembered C, publishes B from A, then accepts C as concurrent. Warning vocabulary is local/UI, not serialized protocol state.

## 16. Cache loss/corruption

HISTORY_MEMORY_LOST requires meaningful evidence of loss/corruption of previously retained or expected advisory state. The optional feature's absence does not qualify. The conditional suite establishes prior retained evidence before injecting loss/corruption; the former ambiguous `v1.history.absent-cache.001` is replaced by `v1.history.memory-lost.001`.

Capability claimants must produce equivalent diagnostic state under specified conditional inputs; user-visible English strings remain non-normative and UI surfacing is SHOULD. Cache corruption is discarded, cannot authenticate objects, and cannot change current H. Cache update failure does not revoke publication. Deliberate clearing loses warning capability only; a conditional trial verifies current conflict remains unchanged.

## 17. Removal of continuity/persistence gates

The model deletes continuity-unknown and persistence-blocked state, not merely their checks. The strict schema removes those actions/results and the unavailable-current-value enum. Misleading block IDs are removed/replaced. Concrete current graph-integrity failure remains an operation stop, separate from advisory cache health.

## 18. Removal of durable graph transaction

Section 36 replaces validation → durable graph commit → authority with accepted evidence in process. Object publication acknowledgement is independent from best-effort cache updates. There is no journal orphan, durable insertion success prerequisite, persistence attestation, or cache transaction recovery protocol.

## 19. Publication ambiguity

Unacknowledged publication is not reported successful; bytes may or may not have become visible. The client may retry exact bytes or repeat the logical operation. Retry-created siblings follow normal graph rules. No reconciliation bit, fence, rescan-before-authoring requirement, or poisoned session survives. The ambiguity case attempts B, receives non-success, publishes C, and later observes B.

## 20. Writer self-validation boundary

External bytes use the unchanged reader/crypto path. A writer must construct correct canonical signed bytes, but production self-decryption, parsing, signature recomputation, or rereading are optional hardening. Writer correctness is established by canonical/signature-input vectors, roundtrip tests, and independent interoperability evidence; fixed vectors were not regenerated.

## 21. Object-publication durability

Complete exact bytes, canonical names, ordinary-file collision checks, and immutable no-overwrite/complete visibility remain MUST obligations. New-object file/directory fsync becomes SHOULD reliability guidance. ALREADY_PRESENT_EXACT needs only exact intended bytes at the canonical ordinary-file target. No existing-file fsync, reread after fsync, or inode proof is normative. Local trials test exact, different, symlink, new, and ambiguous outcomes; existing content is never clobbered.

## 22. VAULT durability

VAULT retains complete staged bytes, file barrier, atomic install/replacement, and directory barrier (or equivalent platform mechanism), with no partial in-place rewrite. Rewrap retains K_root and fresh salt/nonce. Repeated identity proofs and mandatory rereads are removed; final cryptographic reopen is optional recommended defense. Old same-root bootstrap copies/passwords remain usable.

## 23. VAULT_BINDING simplification

There is no PENDING state. Authenticate canonical VAULT; absent binding allows durable first-open establishment; existing binding requires exact equality. Malformed/unreadable present anchors do not become absence. A crash after VAULT publication but before binding creation resumes as first open. Local binding trials exercise absent, not-yet-durable, authentication failure, corrupt, mismatching, and matching anchors.

## 24. Private-key custody

Device keys remain private, bound to the vault, crash-safe at creation, protected by local permissions/platform custody, and resistant to accidental replacement. P-256, DEVICE_ID, signature contexts, ECDSA acceptance, and signing nonce requirements are unchanged. Optional retained public keys can verify provenance without becoming current DEVICE presentation nodes.

## 25. Initial DEVICE prerequisite

First TOKEN setup success requires matching assertion-valid correctly self-signed DEVICE and TOKEN local publication acknowledgements. The existing workflow keeps wrong-key/invalid/nonacknowledged negatives and both publication orders. It no longer uses durable graph records or claims peer propagation. Later DEVICE loss may leave remote provenance unresolved without invalidating TOKEN state.

## 26. Opaque/future evidence policy

All classification boundaries remain: supported invalid, routable future TOKEN, routable future DEVICE, authenticated unscoped future, and unknown sibling family. Unscoped evidence must be disclosed but does not globally block ordinary TOKEN operations. Routable current opaque TOKEN remains a scoped block. Exact opaque retention is optional. Wrong-size/current-family unauthenticated bytes can never become opaque evidence.

## 27. Rebaseline/reset removal

Security-critical reset/baseline epochs, complete replacement scan transactions, opaque evidence stickiness, and journal tail/persistence recovery are removed. Optional history may be discarded with an explanation of lost regression detection. Current objects and their causal meaning are unchanged by cache reset; missing intermediates may already expose older heads in the accepted snapshot.

## 28. Readiness predicate changes/removal

BASE_OPERATION_SAFE, AUTHORITATIVE_VAULT_READY, and CANDIDATE_USE_READY are removed from current normative text and model. Direct per-operation requirements replace them. Storage/state-query integrity_ok reports only concrete graph consistency, not a new global readiness abstraction. Candidate use pins an authenticated supported LIVE object and discloses uncertainty.

## 29. Wire/crypto invariance

The independent audit compares entire committed r14 byte-bearing case files, not reconstructed output from the modified model. All 44 crypto/dispatch/bootstrap/provenance/signature-context/capacity/TOTP/late-provenance fixtures are byte-identical. Zero changes to VAULT bytes, semantic bytes, signatures, signature inputs, OBJECT_IDs, encrypted objects, or TOTP answers. Unchanged crypto/object/TLV/TOTP source and test files are also compared byte-for-byte.

Structural checks pin entire unchanged wire/crypto sections and selected wire code blocks directly to r14 SHA-256 fingerprints. Historical r14-and-earlier revision prose is byte-identical. No crypto/vector generator was run. Synthetic local API trial buffers are transport-model inputs, not new encrypted protocol vectors.

### Baseline vs conditional advisory-history conformance

Review found optional history was described correctly in prose but every history-warning case was still pinned as baseline. The corrected manifest assigns each case exactly one schema-validated applicability. A client with no cache can run baseline with history support disabled. Conditional cases have real expected results when `advisory-history` is claimed; no SKIP or ignored failure is introduced.

All 98 prepared case files were inspected for history actions and warning expectations. ## 31. Reference-model changes

The graph model now contains accepted nodes/values, concrete integrity failure, and separate optional warning evidence. Learn has no persistence parameter. Supported accepted observations require complete values; missing remembered objects do not survive in the graph. Snapshot/Plan select parents before later observations. Confirmation context contains only TOKEN semantics/intent. Publication acknowledgement adds local objects without a cache commit. Same-ID contradictions, resolved cycles, all-head DEVICE rename, and provenance independence remain tested.

Removed machinery includes replacement baseline state, continuity/persistence gates, mandatory opaque byte store/reprocessing, durable insertion APIs, and reset tests. The monolithic r14 vector generator was removed because it encoded obsolete state contracts; its fixed outputs remain pinned. The portable consumer remains a semantic model, not a production filesystem adapter or full fold scheduler.

## 32. Conformance changes

Baseline conformance does not require advisory history. The moving-pre-RC profile contains exactly the 93 manifest baseline IDs/hashes, while the complete manifest separately pins 12 conditional advisory-history cases. Implementations can claim baseline without implementing that capability, retaining cross-run history, or emitting history-loss/regression/cache diagnostics.

The reference model declares `ReferenceCapabilities = ["advisory-history"]`. Default execution selects baseline and disables history actions; capability selection adds conditional cases. `make conformance` runs baseline; `make conformance-all` (CLI `-capability advisory-history`) runs baseline plus the conditional suite. Output identifies `capability=advisory-history`. `make check` and model tests exercise both selections.

Strict manifest applicability requires baseline with no capability, or conditional with exactly the recognized advisory-history capability. Unknown properties, capabilities, missing classifications, duplicate IDs/paths, profile/manifest baseline-set disagreement, and unlisted physical cases reject. Expected results remain independent from applicability. No additional profile or wire negotiation is introduced.

Structural guards assert that clients without history remain baseline conforming and reject mandatory retention claims. Crypto/wire guards and concrete graph integrity remain unchanged. Go race tests remain implementation race evidence, not synchronized freshness proofs.

## 33. Security tradeoffs

r15 intentionally gives up hard blocking after loss of previously remembered history. Established clients can continue after advisory memory loss; regression detection becomes best effort, resembling fresh-installation limitations. A write made against an older accepted subset may later conflict when hidden history reappears.

Mitigations remain concrete: immutable no-overwrite objects, unchanged authentication/cryptography, exact signed causality, normal DAG concurrency/conflict interpretation, and warnings where regression evidence exists. No local mechanism claims synchronized completeness. This is not a wire downgrade: it removes unsupported global conclusions from local observations.

## 34. Downstream implementation impact

Non-normative guidance for later downstream work: replace the durable graph journal security boundary with an optional cache; remove continuity/persistence/global discovery/unscoped gates, ordinary final frontier rechecks, and publication reconciliation fences; narrow confirmation to TOKEN semantic context; make runtime self-reader roundtrips optional; use first DEVICE local acknowledgement; remove synchronized `syncExistingFile` durability obligations; simplify establishment by removing PENDING. Preserve strong VAULT/binding/private-key custody and durability. No exact Java class architecture is prescribed and no Java files are edited.

## 38. Issues/blockers

During review, advisory history was found to be described as optional while all history-warning cases were still pinned as baseline. The corpus/profile was corrected to classify advisory-history-dependent cases conditionally. Mixed cases were split so baseline accepted-snapshot and authority-separation requirements remain mandatory. Section 37's requirement delta labels history retention as removed from baseline and cache-loss/regression diagnostics as conditional capability behavior.

No r15 semantic rollback, new wire behavior, or frozen-fixture change was introduced. No known blocker remains. The 93 baseline and 12 conditional cases pass; optionality is executable, not merely prose.

This report and its machine-readable audit remain uncommitted pending review. No downstream implementation was edited. Independent implementation and production platform durability evidence remain pre-RC work.

Advisory remembered history is an optional local capability. Baseline Totipo v1/r15 implementations derive protocol state solely from accepted authenticated snapshots and need not retain cross-run graph history.

Implementations that claim the advisory-history capability must treat remembered state only as regression-warning evidence and must never let it become authoritative current protocol state.
